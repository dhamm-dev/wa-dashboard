# Revocation cleanup: isolated manifest design

Status: design only. The fixture in `test/fixtures/revocation-manifest-design.sql` is not a migration or a cleanup implementation. The endpoint remains pending and deletes nothing.

## Inventory and journal

After acquiring the existing exclusive instance lock and before any recovery, reconnect, worker, or listener, use one SQLite `BEGIN IMMEDIATE` transaction per pending user to enumerate accounts by `owner_id`, upload IDs from `upload_files`, and legacy attachment IDs not represented there. Include account IDs even when no uploads exist. Record the ownership relationship with each item. Reject malformed UUIDs, ambiguous ownership, inconsistent attachment/upload account associations, or references crossing owner boundaries; do not silently omit them. The transaction creates and seals the complete inventory atomically, or leaves no inventory. Existing pending revocations must be inventoried on startup, not only new requests.

The fixture demonstrates append-only manifest rows, a seal with count and digest, and an ordered append-only progress journal. The real implementation must compute and verify a SHA-256 digest over a versioned, unambiguously encoded, deterministically sorted inventory including user ID and request timestamp. It must validate types, UUIDs, ownership and completeness in the same transaction before sealing; the fixture intentionally does not implement these checks. A sealed inventory must never be regenerated after deletion starts. Journal transitions are recorded only after durable completion of the corresponding work; retries operate from the sealed inventory. Partial filesystem progress is retried idempotently. A final database transaction deletes known owned records in foreign-key order, preserves tombstones, and records database completion atomically. Verify every affected row and fail closed on inconsistencies.

## Scope

Candidate files are `uploads-v2/<upload-id>/data` for inventoried upload rows, `uploads/<attachment-id>` for inventoried legacy attachments, and WhatsApp auth data under the exact inventoried account directory. Only recognized, owned auth-store entries should be removed; unexpected entries block completion rather than being recursively swept. Known database records include user-owned templates and account-owned contacts, uploads, attachments, schedules, history and history events, bot settings/keys/generation/reservations/welcomes, and credentials. Inspect all current foreign keys and triggers before implementing deletion. Leave unassociated orphan files, unknown directory entries, backups, logs, SQLite WAL and database free pages outside the cleanup claim. Logical deletion is not secure erasure.

## Safety gates still required

* Prove a filesystem deletion mechanism that resolves every component relative to trusted open directory descriptors, rejects symlinks and unexpected file types, and is safe against replacement races. Node path-based `lstat` followed by `unlink` or recursive `rm` alone is insufficient. Durably sync modified directories before journaling completion; missing items must be safely distinguishable from unsafe traversal.
* The current `revoked_users.user_id` foreign key prevents deleting the user row. Define a transactional migration to preserve an immutable user-ID tombstone independently, plus Google subject and normalized email identity tombstones. Email registration and both Google login paths must check the appropriate tombstones transactionally. Do not remove email credentials until registration is protected.
* Audit startup imports for side effects and enforce cleanup after the exclusive lock but before `initMediaTemp`, upload recovery, pending recovery, worker tick, reconnection, and listen. The lock only coordinates cooperating processes using the same canonical `DATA_DIR`; operations must stop any older process that does not honor it.
* Test real cleanup with synthetic temporary directories: live-lock contention, crash at each journal/filesystem/transaction boundary, reruns, UUID traversal, symlink and directory substitution, shared/cross-owner references, old and new uploads, credential re-registration, other-owner preservation, and accurate status on failure. Inject failures without using production data. The present fixture tests only the inventory/journal constraints, not deletion or the digest.
